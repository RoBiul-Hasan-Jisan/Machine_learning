# Solutions — 04 Regularization

1. In the unregularized plot, training loss keeps decreasing smoothly throughout, but validation loss decreases initially, reaches a minimum somewhere in the early-to-middle portion of training, then starts climbing back up while training loss continues to fall — this widening gap is the visual signature of overfitting. The exact epoch varies by run, but it's typically well before the end of the 800 epochs.

2. With `l1=0.01`, a meaningfully larger number of weights in `net_l1.W1` should end up very close to exactly zero (e.g. `< 1e-3`) compared to `net_l2.W1`, whose weights are shrunk but rarely reach exactly zero — this matches the theory: L1's constant-magnitude gradient keeps pushing small weights all the way to zero (sparsity/feature selection), while L2's gradient shrinks proportionally to the weight's own size and flattens out near zero.

3. With `dropout_p=0.7`, the *training* loss curve itself typically becomes much noisier and converges to a noticeably higher final value than with `dropout_p=0.3` — because at each step, 70% of hidden neurons are randomly zeroed out, severely limiting the network's effective capacity on that particular forward pass. If dropout is too aggressive, the network can no longer fit even the training data well (underfitting), since it rarely gets to use enough of its neurons together at once to represent the function it needs to learn.

4. With `patience=5`, early stopping typically triggers very early, potentially before the model has had a chance to reach its true best validation loss (premature stopping, underfitting risk) — validation loss can be noisy epoch-to-epoch, and a short patience window can mistake a temporary uptick for the true turning point. With `patience=200`, early stopping essentially becomes a no-op for an 800-epoch run and behaves close to standard full training, risking the exact overfitting early stopping was meant to prevent. The sweet spot balances catching the true minimum against being too trigger-happy on noisy fluctuations.

5. `noise_std=0.01` likely helps the least, since it barely perturbs each point at all — augmented points are nearly identical to the originals, adding very little genuinely new variation for the model to learn from (little regularizing benefit). `noise_std=1.0` risks the opposite problem: with jitter that large relative to the moons' spread, augmented points can drift far enough to actually cross into the "wrong" class's region of space — violating the label-preserving assumption and effectively injecting label noise, which can hurt rather than help generalization.

6. At inference/test time with a single input (batch size 1), computing `mu`/`var` "live" from that one example is meaningless (variance of a single point is 0, causing division issues, and there's no real "batch" to normalize against) — normalizing a single sample this way would produce nonsensical, unstable outputs. PyTorch's `model.eval()` switches BatchNorm layers to use *running* mean/variance statistics accumulated as exponential moving averages *during* training (across many batches), rather than the current batch's statistics — giving a stable, batch-size-independent normalization at inference time.
